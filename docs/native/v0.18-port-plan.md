# 移植到上游 v0.18.0：现状与剩余工作

本文记录把 `upstream/photocraft` 从 v0.16.0 升到 v0.18.0 的实测结果。所有数字都来自本机实际编译，不是估算。

## 一、已完成

| 项 | 状态 | 证据 |
|---|---|---|
| 内置上游替换为 v0.18.0 | 完成 | `upstream/photocraft/Cargo.toml` `version = "0.18.0"` |
| 四个补丁（宿主扩展点 / 引擎钩子 / 字体 / 沙箱与外观） | 完成、双架构通过 | `patches/0001`–`0004`，重放 0 拒绝 |
| 适配层 50 个编译错误 | **清零** | `cargo check` 与 `--tests`，arm64 + x86_64 |
| 双架构静态库 → HAP | 完成 | `entry-default-unsigned.hap` 135 MB，见第三节 |
| 上游自己的 UI 单测在本机跑通 | 完成 | `cargo test -p photocraft-ui-egui --lib`：4,478 通过 / 0 失败 / 21 忽略，见第三节之二 |
| 适配层版本固定改为 0.37 / 30.0.1 | 完成 | `scripts/upstream_sync.py pins --write` |

补丁 0001 把 v0.16 版移植里「手工把一帧拆成三份」的工作正式变成了上游扩展点：

```

cargo check -p photocraft-ui-egui --no-default-features --target x86_64-unknown-linux-ohos    # 通过
```

规模对比很关键：

## 二、五层的去向：四个补丁 + 适配层改写

把 `native/rust` 指向 0.18 实测报过 50 个错误。现在这些错误全部清零，做法是「上游缺的补丁补，上游已有的不重复实现」。

| 层 | v0.16 的规模 | v0.18 的做法 | 结果 |
|---|---|---|---|
| 手写笔 | 1106 行 | **不加补丁**，适配层 223 行直接投 `StylusFeed::set` | 完成，见 `host-stylus.md` |
| 沙箱文件 | 914 行 | `patches/0004` 补 `Services` 的 `pick_*` / 路径字段 + `ask_file` 同步直答 | 完成 |
| 窗口外观 | 1071 行 | `patches/0004` 补 `window_fullscreen`、`host_titlebar`、`native_doc_windows`、`chrome_css` | 补丁完成；**菜单折叠成汉堡、手指隐藏笔轮廓未移植** |
| 字体与语言 | 286 行 | `patches/0002` + `0003`：`set_host_locale`、`set_ui_locale`、`store_host_cjk_font`、`reapply_host_fonts` | 完成 |
| 引擎与格式钩子 | 144 行 | `patches/0002`：`set_app_profile_dir`、`format::atomic::set_host_writer`、`print_spooler` | 完成 |

三处**明确不做**的，写在这里而不是留个空实现：

1. **菜单栏折叠成汉堡**（fork 的 `menus.rs` 386 行改）：这是手机竖屏的观感需求，不是编译阻塞。0.18 的菜单栏仍是桌面布局，需要单独设计一轮（见第四节）。
2. **手指按下隐藏笔轮廓**（fork 在 `canvas.rs` 里加的规则）：属于上游 canvas 层行为，0.18 没有这个概念（它按 pointer 事件画，不看是谁在按）。
3. **标题栏笔菜单 / `stylus_debug` 窗口**：0.18 没有消费方，适配层只保留解析。

### 另有一批与版本升级直接相关的 API 漂移（与鸿蒙无关）

| 位置 | 0.16 → 0.18 | 适配层改法 |
|---|---|---|
| `egui::Event::MouseWheel` | 新增必填 `source` | 轴事件 `MouseWheelSource::Unknown`，滚轮 `Wheel` |
| `egui::output::IMEOutput` | 新增 `owner` / `context_generation` / `reset_request` / `change_cause` / `surrounding_text` | 按上游字段填，无宿主语义的用默认值 |
| `egui_wgpu::RenderState` | 不再有 `surface_config`（移到 `WgpuConfiguration`） | 删掉这行赋值 |

| `ui-egui` 的 `DocWindow` | 新增 `floating` / `focused` | 子窗口测试补齐字段 |

| `i18n` | 语言从系统探测改为 `set_host_locale` 显式注入 | `patches/0002` |

这几处必须按 0.18 的新写法改，不能沿用旧调用。

## 三、HAP 已经打出来了

2026-11-02 实测（Windows 11 + DevEco Studio SDK API 26 + Rust 1.99.1），一条命令走完原生库和打包：

```
scripts/dev.sh build      # cargo release × 2 ABI → cmake/ninja → hvigor assembleHap
```

产物 `entry/build/default/outputs/default/entry-default-unsigned.hap`，**135 MB**（2026-11-02 第二次全量构建复测）：

| 项 | 值 |
|---|---|
| `libs/arm64-v8a/libphotocraft.so` | 60 MB |
| `libs/x86_64/libphotocraft.so` | 71 MB |
| 调试信息 | 已 strip（`llvm-readelf -S` 无 `.symtab` / `.debug*`） |
| `module.json` | `deviceTypes: phone, tablet, 2in1`；target/compatible 26 |
| `scripts/verify_native.py` | 通过（bundle 名 + 两个 ABI 的 ELF 机器码都核对） |

打包链上两个只在本机会踩的坑，都写进 README 了：

1. **API ≥ 26 的 SDK 要求 `compatibleSdkVersion` 写成 `"26.0.0"`**。`"6.0.0(26)"` 报 `api version parameter is illegal`，`"26"` 报 `Specification Limit Violation`，只有三段式通过。
2. **`PackageHap` 用 `spawn java` 找 Java**，只设 `JAVA_HOME` 不够，PATH 里必须有 `java`；`scripts/dev.sh` 现在把 `$JAVA_HOME/bin` 前置进 PATH。

## 三之二、宿主单测：4,478 通过 / 0 失败

补丁只有不改变上游行为才有意义，所以除了「能编过、能打包」，还跑了上游自己的 UI 单测：

```
cargo test -p photocraft-ui-egui --lib      # 4,478 passed, 0 failed, 21 ignored（95 秒）
```

`tools::type_tool::canvas_tests::multi_layer_formatting` 里有两个用例用 `Harness::run`（默认 8 步），在 6 线程全量跑时偶尔要多等一帧（字形栅格化晚了）而报 `exceeded max_steps`；单独跑该模块 3/3 通过，重跑全量也通过。这是上游测试的步数上限与机器负载的关系，没有改上游测试。

这一步曾一次性报 24 个失败，逐个查完是三类，都不是补丁改坏了上游：

| 现象 | 数量 | 原因 | 处理 |
|---|---|---|---|
| `No glyph for "文" (U+6587)` 之类 panic | 22 | 缺可选的 craft-fonts 构建输入。上游的界面用例按「有系统 CJK 字体」写，并在缺字形时直接 panic；上游 `docs/development.md` 也要求 CI 的 Windows 腿带上 `CRAFT_FONTS_DIR` | 克隆 `storytold/craft-fonts`，用 `CRAFT_FONTS_DIR=<绝对路径>` 重跑，22 个全过 |
| `i18n::system` 两条断言 | 2 | **是自己写错**：`?lang=` 的用例拿 `sv-SE` 当「不支持的语言」，但 0.18 有瑞典语目录，`resolve` 正确地返回 `sv` | 改用确实没有目录的 `sw-KE`，断言仍是「覆盖不回退到浏览器列表」 |
| `window_fullscreen` 断言图标存在 | 1 | 也是自己写错：`icon()` 返回的 `fullscreen-enter` / `fullscreen-exit` 在 `assets/icons` 里根本不存在 | 删掉 `icon()`：菜单项本来就没有图标位，命令改成从 View › Screen Mode（`F`）触发 |

顺带修了两个真问题：`view.screenMode.*` 原先只发 `ViewportCommand`，对「自己拥有窗口」的宿主是空操作，现在有 `Services::window_fullscreen` 时直接向宿主请求全屏（鸿蒙侧这才真的能进全屏）；`path_pick.rs` 里 3 处废弃的 `egui::Id::new` 改成 `Id::unique`，编译告警清零。

本机环境还有一条干扰，记在这里免得下次误判：`crates/text/src/cjk.rs` 的 `os_locale()` 在 Windows 上起 `reg.exe` 读 `LocaleName`，被安全策略拦掉。它只影响「跟随系统语言」的探测，鸿蒙侧一直用 `set_host_locale` 显式注入语言，所以不影响应用，也不影响单测。

## 五、为什么不再用「整树分叉」

v0.16 的做法是把上游拷成一份 7620 行的分叉。这次量出来：上游 v0.16→v0.18 改了 58 个文件、72 个冲突块，还把 `ui-egui` 从约 400 个扁平文件重排成 120 个文件加子目录，于是 14 个被改过的文件直接变成 `modify/delete`。单 `lib.rs` 重放 54 个补丁块有 47 个失败。

改成「pristine 上游 + 小补丁」后，同样的升级只需要重放一个 150 行的补丁。上游 0.18 甚至已经在 `logic_frame`/`ui_frame` 的注释里写明「包装型宿主自己调用尾部」，说明这条路是上游认可的。
